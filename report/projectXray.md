## 二、核心发现一：一个 bot 只做一件事

**两个 bot 的分工极端专一：**

| bot | 消息数 | 职能 |
|---|--:|---|
| 仓库中继 | 10 | **把 issue / PR 原文搬进群** |
| **单规则执行** | **2** | **「请不要发送带有哭泣表情符号的贴纸。」** |

**第二个 bot 值得单独记录。**

**它的名字直译就是"反哭泣 bot"，而它在样本中发出的两条消息内容完全一致——它只会说这一句。**

**本语料此前记录的 bot 用途有七种：**

| 用途 | 样本 |
|---|---|
| 播报 | [M_Team_Chat](M_Team_Chat.md)（站点资源池状态） |
| 群管 | [gouwu](gouwu.md) 等（通用清理） |
| 关键词服务 | [v2rayN](v2rayN.md)（「下载」「文挡」） |
| 反诈 | [gouwu](gouwu.md)（提示） |
| 门禁 | [nexitallyusers](nexitallyusers.md)、[wikipedia_zh_n](wikipedia_zh_n.md) |
| 定时禁言 | [ruanlu](ruanlu.md)（每晚到 7 点） |
| 垃圾分发 | [pdcn2](pdcn2.md)（属于入侵者） |
| **单一微规则执行** | **projectXray** |

**第八种与"群管"的区别是范围：** **群管 bot 处理的是违规（广告、辱骂、刷屏）；这一个处理的是一条审美/氛围上的偏好。**

**"不要发带哭泣表情的贴纸"不是安全问题，也不是垃圾问题**——**它是一个社群对自己聊天氛围的具体要求，而有人为它写了一个 bot。**

**这件事的信息量在于它揭示了这个社群的治理密度：**

> **当一个群会为"贴纸里的表情不对"部署专门的自动化时，说明它的其他治理问题已经解决完了。**

**对照本批的 [pdcn2](pdcn2.md)（218 条垃圾全部存活、零治理）——** **同样是技术主题的中文群，一个连博彩广告都不管，一个连贴纸的情绪都管。**

**本语料由此可以给"群治理投入"排一条谱：**

| 档 | 表现 | 样本 |
|---|---|---|
| 0 | 放任一切 | [pdcn2](pdcn2.md)、[ibetame](ibetame.md) |
| 1 | 靠话题门槛自然过滤 | [pythonzh](pythonzh.md)、[BotTalk](BotTalk.md) |
| 2 | 事后人工清理 | [GIFgroupTW](GIFgroupTW.md) |
| 3 | 自动化拦截（门禁、定时禁言） | [wikipedia_zh_n](wikipedia_zh_n.md)、[ruanlu](ruanlu.md) |
| **4** | **为单条氛围规则做专门自动化** | **projectXray** |

## 三、核心发现二：全文中继与工单号标签

**仓库中继 bot 搬的不是标题，是全文。**

**样本中最长的三条都来自它：2,785 / 2,509 / 996 字符。** **2,785 字符那条把一个 issue 的完整正文搬了进来，包括动机说明、对其他两个工单的交叉引用（`#6265` `#6409`）、以及目录结构示例。**

**正文中位只有 9 个字，而最大值 2,785**——**这是本语料最极端的双峰分布。** **群里的人类发的是几个字的短句，bot 发的是近三千字的技术文档。**

**标签全部是工单编号：`#6788` `#6789` `#6790` `#6787` `#6748` `#6265` `#6409`，外加一个 `#issuecomment`。**

**本语料的"标签十一用"**（[iingtw](iingtw.md) 第四节确立第十一种"修辞标签"）**在这里出现第十二种：工单编号标签。**

**它的三个特征：**

1. **机器生成**——编号来自上游系统，不由人选择。
2. **一次性且唯一**——每个工单一个标签，不复用。
3. **可检索且精确**——**知道编号的人可以直接在群里搜到那条讨论。**

**它与本语料已记录的编号标签**（[nicegramchat](nicegramchat.md) 的 `#232`、[SteamNy](SteamNy.md) 的 `#NS2682`）**的区别是：那两个的编号含义不可知，这一个的编号在一个公开系统里有确定含义。**

**本语料由此把编号标签分成两类：**

> **内部编号**（含义仅内部人知）与**外部系统编号**（含义在一个公开系统里可查）。
> **后者才真正具备检索价值，因为读者可以独立验证编号指向什么。**

**这个设计的实际效果是：这个群成了那个代码仓库的一个可搜索镜像。** **一个不想开代码托管平台的人，可以在 Telegram 里读到完整的 issue 正文并按编号跳转。**

**本语料在 [zhihuribao_rss](zhihuribao_rss.md) 第五节记录过 Telegraph 全文镜像（"链接处理六档"的第四档：为读者做代理）。这是同一动机的另一种实现：**

| 样本 | 镜像什么 | 载体 |
|---|---|---|
| [zhihuribao_rss](zhihuribao_rss.md) | 文章全文 | **Telegraph 页面** |
| **projectXray** | **issue / PR 全文** | **群消息本身** |

**第二种更彻底：内容不离开 Telegram，连一个外部页面都不需要。**

## 四、核心发现三：技术在 bot 里，人在聊别的

**样本中人类发言的主线是什么？**

**逐条看下来，最长的一段连续对话是关于外卖包装的密封问题：**

> 「所以现在外卖基本都打了封条」
> 「不至于吧，现在外卖都是密封口」
> 「大型连锁店基本都是有密封口的」
> 「除非完全密封，不然一根小管子的事情。都是防君子不防小人的。」

**这与群名指向的项目没有任何关系。**

**结合代码托管域名只出现 25 次（其中绝大部分来自 bot 的中继）、正文中位 9 个字、以及 33 个文件全是贴纸与短视频，可以确定：**

> **这个群的技术内容全部由 bot 提供，人类成分是闲聊。**

**本语料的技术群样本对照：**

| 样本 | 技术内容来源 | 人类发言 |
|---|---|---|
| [pythonzh](pythonzh.md) | **人**（具体的技术问答） | 技术 |
| [BotTalk](BotTalk.md) | **人** | 技术 |
| [loveapps](loveapps.md) | **人**（短问答） | 技术 |
| [V2EXPro](V2EXPro.md) | 无 | 观点 |
| **projectXray** | **bot** | **闲聊** |

**这是本语料第一个"技术内容与人类发言完全分离"的技术群。**

**它的成因可以推出来：这个项目的实际技术讨论发生在代码托管平台上**（issue 正文里有完整的动机论证与交叉引用）。**Telegram 群不是讨论场所，是通知场所 + 休息室。**

**本语料在 [cool_scripts](cool_scripts.md) 第九节把"产品带社区"分成"用户群"（双向、有支持成本）与"通知流"（单向、零支持成本）两支。**

**这个样本是一个混合体：**

> **通知流 + 休息室。** **bot 负责通知，人负责社交，两者在同一个版面上互不干扰。**

**存活率 69.3% 与 37 个发言人 / top10 占 76% 支持这个判断：** **一个有固定熟人核心、话题随意、但没有垃圾问题的群。**

## 五、核心发现四：与协议层频道的配对

**这个群与本语料已收录的 [projectXtls](projectXtls.md) 指向同一个开源项目。**

**本语料在 [ClashR_for_Windows_Channel](ClashR_for_Windows_Channel.md) 第三节做过中文代理生态的六层垂直切分，并得出"变现能力与代码贡献度成反比"：**

| 层 | 样本 | 推广链接数 |
|---|---|--:|
| **协议** | **[projectXtls](projectXtls.md)** | **0** |
| 规则集 | [ACL4SSR](ACL4SSR.md) | 约 5–7 |
| 客户端 | [surfboardnews](surfboardnews.md) | 0 |
| 配置工具 | [QuanX_API](QuanX_API.md)、[cool_scripts](cool_scripts.md) | 0 |
| 本地化/版面 | [ClashR_for_Windows_Channel](ClashR_for_Windows_Channel.md) | 176 |
| 测试/广告位 | [speedcentre](speedcentre.md) | 271 |
| 分发 | [zaproshare](zaproshare.md) | 232+ |

**这个样本补上了协议层的第二个观测点，而结论一致：零推广链接、零收款、零联盟参数、零机场推广。**

**代码托管 25 次是它的最高频域名，其余三个域名合计 5 次。**

**本语料由此可以把那条结论说得更确切：**

> **不是"写代码的人不变现"，而是"离代码越近，可用于变现的版面越少"。**
> **协议层的版面全部被技术内容占满了**——**这个群里唯一的"广告位"是 bot 发的 2,785 字 issue 正文。**

**对照 [speedcentre](speedcentre.md)（271 个推广链接）：那个号的版面全部是可售的，因为它不产出技术内容。**

## 六、实现技术思路

| 层 | 做法 |
|---|---|
| 技术内容 | **仓库 webhook → 群，全文中继** |
| 检索 | **工单编号自动成标签** |
| 治理 | **两级：通用（不可见，但存活率 69.3% 说明存在）+ 单规则 bot** |
| 人类内容 | **闲聊，零组织** |
| 自有基础设施 | **零域名、零服务器**（两个 bot 均为第三方/自建但不可判定） |
| 外链 | **代码托管 25 次，其余 5 次** |

**全文中继是一个有代价的设计选择：**

**好处是群内可搜、不依赖外部页面、读者不用跳转。**
**代价是 2,785 字符的单条消息会把手机上的聊天界面整屏占满**——**在一个 300 条/天的群里，这会严重干扰人类对话。**

**样本中 bot 只占 4%（12 条），说明中继频率不高，这个代价是可接受的。**

**但它同时解释了第四节的现象：** **当一条 bot 消息能占满一屏时，人类不会在它后面接着讨论技术细节**——**技术讨论自然回到了代码托管平台上。**

**本语料由此得到一条设计层面的观察：**

> **中继的完整度与社群的讨论活性可能是负相关的。** **搬得越全，群里越没必要讨论。**

**这与 [cool_scripts](cool_scripts.md) 的对照很直接：那个频道搬的是变更摘要（正文中位 183 字），而它的评论也很冷清（12 帖 / 48 条）。** **两个样本同向。**

## 七、成本

**经常性（月）：¥0–100。**

| 项目 | 金额 | 依据 |
|---|--:|---|
| 仓库中继 bot | ¥0–50 | webhook 转发，可在最小规格机器上运行；也可能用现成服务 |
| 单规则 bot | ¥0–50 | 功能极简 |
| 群管理 | **¥0** | 存活率 69.3%，无高强度清理迹象 |
| 域名 / 服务器 | **¥0** | 零自有 |

**这是本语料成本最低的有自动化的群。**

**对照 [ruanlu](ruanlu.md)（定时禁言 bot，第三方免费档）、[wikipedia_zh_n](wikipedia_zh_n.md)（入群验证码）——**那两个用的都是通用工具；**这个群的两个 bot 都是为这个项目定制的。**

**定制的成本不在服务器上，在写它的那几个小时里，而那是开源项目的日常。**

**本语料在 [cool_scripts](cool_scripts.md) 第七节记录过同一个结构：频道本身几乎零成本，但它是一个有真实开发成本的项目的附属品。**

## 八、收益

**可观测：¥0。**

**300 条里零收款账号、零联盟参数、零推广码、零机场推广、零广告。** **1 条粗筛命中为误报。**

**这与协议层的另一个样本 [projectXtls](projectXtls.md) 完全一致。**

**本语料"不变现十二种类型"**（[SteamNy](SteamNy.md) 第四节确立第十二种）**中，它属于"不该变现"一类**（与 [QuanX_API](QuanX_API.md)、[tginfoen](tginfoen.md)、[cool_scripts](cool_scripts.md) 同组），**但成因比那三个更硬：**

> **前三个是"变现会损害可信度"**（一个选择）。
> **这一个是"没有可售的版面"**（一个事实）。

**未变现的承载力：¥300–2,500/月。**

**四条依据：**

1. **人群质量极高**：1.58 万成员的核心协议项目讨论群，**其中包含实际提交 PR 的开发者。**
2. **但可售版面极少**：**唯一的固定位置是 bot 消息，而把广告插进 issue 中继会立刻破坏这个 bot 的唯一用途。**
3. **群的实际参与规模只有 37 人**（top10 占 76%），**与 1.58 万的名义规模差两个数量级。** **本语料在 [ruanlu](ruanlu.md) 第八节遇到过同一问题（1.79 万名义 vs 24 人实际）。**
4. **政治性约束**：**这个项目在本语料 [projectXtls](projectXtls.md) 第三节记录的 2026-07 声明中明确表达过对使用地域的限制立场。** **一个有明确立场的项目，其社群接受商业投放的可能性很低。**

**区间宽的原因：本语料没有任何协议层项目的商业化定价样本，因为这一层从来没有人卖过。**

## 十、法律风险

**风险等级：中。**

- **项目性质：核心代理协议实现（主要考量）。** 与本语料 [projectXtls](projectXtls.md) 第九节的分析一致：**这是一个通用网络传输协议的开源实现，具有明确的合法用途**（企业内网穿透、抗审查通信、隐私保护），**不符合《刑法》第 285 条第 3 款"专门用于侵入、非法控制计算机信息系统"的"专门性"要件。**
- **但它比配置工具层更靠近核心。** **本语料的六层切分中，这是最上游的一层**——**下游的机场、客户端、规则集都依赖它。** **在司法实践中，越上游的通用工具越不容易被追究，因为通用性越强；但同时它的影响面最大。** **这两个因素方向相反，本报告不对最终认定作预测。**
- **群内零推广、零交易。** 300 条中零收款账号、零联盟参数、零机场推广码、零节点分享。**这是它与本批 [ibetame](ibetame.md)（三条带邀请码的机场链接存活）的关键区别，也是它与 [ClashR_for_Windows_Channel](ClashR_for_Windows_Channel.md)（176 个推广链接）的关键区别。** **无营利要件即切断帮信罪与非法经营罪的主要路径。**
- **群主的管理义务：履行情况良好，且有主动措施。** 存活率 69.3%、1 条粗筛命中为误报、部署了两个定制 bot（其中一个专门执行氛围规则）——**这构成"已采取管理措施"的正面证据。** **与 [pdcn2](pdcn2.md) 形成本语料最强的一组对照。**
- **中继内容的著作权。** bot 搬运的是公开代码仓库上的 issue 与 PR 正文，**作者为项目社区成员。** **此类内容通常受项目的协作条款与平台服务条款约束，公开提交即意味着同意公开展示；中继至另一平台并标注编号与作者，落在合理使用与社区惯例之内。** **与 [zhihuribao_rss](zhihuribao_rss.md) 第十节的商业内容全文转载不是同一性质。**
